# Exposing Customer MongoDB Instances Externally Using Envoy Gateway

## 1. Problem Statement / Use Case

We are building a Database-as-a-Service (DBaaS) platform where multiple customers can provision and manage their own MongoDB instances running inside our Kubernetes infrastructure.

Customers should be able to connect to their MongoDB instances from outside Kubernetes using standard MongoDB clients such as:

- `mongosh`
- MongoDB Compass
- MongoDB Go/Python/Java drivers
- Customer applications

For example, a customer should be able to connect using:

```bash
mongosh "mongodb://customer1:<PASSWORD>@lb-1.dbaas.rax.io:30125/admin?authSource=admin"
```

The customer does not need direct Kubernetes access. They only need the connection endpoint and MongoDB credentials provided by our DBaaS platform.

## 2. Understanding the Networking Challenge

Consider three customers with independent MongoDB instances:

```text
Kubernetes Cluster
│
├── customer-1 namespace
│   └── MongoDB Service :27017
│
├── customer-2 namespace
│   └── MongoDB Service :27017
│
└── customer-3 namespace
    └── MongoDB Service :27017
```

All MongoDB instances use the same internal port: `27017`.

This is perfectly valid because Kubernetes Services and Pods have separate network identities.

However, we need to expose these instances through shared external infrastructure.

Suppose all customers connect to:

```text
203.0.113.10:27017
```

How would the external gateway determine which customer's MongoDB instance should receive the connection?

### Why HTTP hostname-based routing does not apply

HTTP proxies can route traffic using application-level information such as:

- HTTP Host header
- URL path
- HTTP headers

For example:

```text
customer1.example.com -> Backend 1
customer2.example.com -> Backend 2
```

MongoDB drivers communicate using the MongoDB Wire Protocol over TCP, not HTTP.

A MongoDB connection does not contain an HTTP Host header or URL path that a generic TCP proxy can use to identify the customer.

Envoy's TCP proxy forwards TCP connections without understanding MongoDB queries, collections or authentication.

Therefore, we need a different routing mechanism.

## 3. Proposed Solution: Unique External Ports

Use one shared public LoadBalancer IP and allocate a unique external TCP port for each MongoDB endpoint.

Example:

```text
Shared LoadBalancer IP: 203.0.113.10

Customer 1 -> 203.0.113.10:30125
Customer 2 -> 203.0.113.10:30126
Customer 3 -> 203.0.113.10:30127
```

Each external port maps to the corresponding internal MongoDB Service.

| Customer | External Endpoint | Internal Backend |
|---|---|---|
| Customer 1 | `203.0.113.10:30125` | `mongodb:27017` |
| Customer 2 | `203.0.113.10:30126` | `mongodb:27017` |
| Customer 3 | `203.0.113.10:30127` | `mongodb:27017` |

The destination port becomes the routing key.

This allows multiple customers to share the same external IP without conflicting with each other.

## 4. End-to-End Connection Flow

```text
Customer Laptop
      |
      | mongosh / MongoDB Driver
      |
      | TCP connection
      v
Public LoadBalancer
lb-1.dbaas.rax.io
      |
      v
Envoy Gateway
      |
      | Listener :30125
      |
      v
TCPRoute
      |
      | Backend mapping
      v
MongoDB Kubernetes Service
      |
      | Port 27017
      v
MongoDB Pod
```

### Step-by-step explanation

1. Customer executes `mongosh` using the connection string provided by DBaaS.
2. DNS resolves the external hostname to the LoadBalancer IP.
3. Customer's MongoDB driver establishes a TCP connection to the allocated external port.
4. Envoy Gateway receives the TCP connection through the corresponding listener.
5. TCPRoute forwards the connection to the correct MongoDB Kubernetes Service.
6. MongoDB receives the MongoDB Wire Protocol messages.
7. MongoDB performs authentication and authorization.
8. Query responses travel back through Envoy to the customer's client.

**Important:** Envoy acts as a Layer 4 TCP proxy. It forwards the TCP stream and does not need to understand MongoDB-specific operations.

## 5. Role of Kubernetes Gateway API Resources

Three important resources are involved.

### A. Gateway

Represents the shared entry point into the Kubernetes infrastructure.

It defines the listeners that accept incoming TCP connections.

Example:

```yaml
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata:
  name: shared-gateway
  namespace: envoy-gateway-system
spec:
  gatewayClassName: eg
  listeners:
    - name: mongo-30125
      protocol: TCP
      port: 30125
      allowedRoutes:
        kinds:
          - kind: TCPRoute
```

### B. TCPRoute

Defines where incoming TCP traffic should be forwarded.

Example:

```yaml
apiVersion: gateway.networking.k8s.io/v1alpha2
kind: TCPRoute
metadata:
  name: customer-1-mongo
  namespace: customer-1
spec:
  parentRefs:
    - name: shared-gateway
      namespace: envoy-gateway-system
  rules:
    - backendRefs:
        - name: mongodb
          port: 27017
```

The Gateway listener accepts traffic on `30125`, and TCPRoute forwards it to the customer-1 MongoDB Service on `27017`.

Cross-namespace Gateway-to-route attachment is controlled through `allowedRoutes`.

### C. ReferenceGrant

Allows specific cross-namespace references where required.

For example, if a TCPRoute references a backend Service in another namespace, the appropriate ReferenceGrant must authorize that reference.

ReferenceGrant is not required merely because the Gateway and TCPRoute are in different namespaces.

## 6. Why Do We Need a Custom Operator?

Manually creating listeners and TCPRoutes for every customer is not scalable.

Imagine supporting hundreds or thousands of MongoDB instances.

We need an automated mechanism to:

- Allocate unique external ports.
- Select one of the available shared gateways.
- Create ListenerSets.
- Create TCPRoutes.
- Track allocation status.
- Handle gateway failures.
- Reallocate ports when necessary.
- Clean up resources when MongoDB instances are deleted.

This is the responsibility of our `liberty-gateway-operator`.

### GatewayPortAllocation CRD

The DBaaS workflow creates a custom resource describing the MongoDB endpoints that need external connectivity.

Example:

```yaml
apiVersion: gateway.liberty.io/v1alpha1
kind: GatewayPortAllocation
metadata:
  name: customer-1
  namespace: customer-1
spec:
  targets:
    - name: mongodb
      serviceName: mongodb
      serviceNamespace: customer-1
      servicePort: 27017
```

The operator watches this resource and reconciles the required networking configuration.

### Operator workflow

```text
GatewayPortAllocation Created
            |
            v
      Validate Request
            |
            v
      Select Gateway
            |
            v
      Allocate Unique Port
            |
            v
      Create ListenerSet
            |
            v
      Wait Until ListenerSet Ready
            |
            v
      Create TCPRoute
            |
            v
      Verify Route Status
            |
            v
      Update CR Status: Active
```

The allocation status records the gateway, external port and corresponding MongoDB endpoint.

## 7. Why ListenerSet Instead of Editing Gateway Directly?

Creating every customer listener directly on a shared Gateway introduces listener-management and scalability concerns.

ListenerSet allows additional listeners to be managed separately from the Gateway's original configuration.

The operator can create and manage ListenerSets for individual allocations without continuously modifying the shared Gateway resource.

This provides better separation of ownership and simplifies lifecycle management.

## 8. Replica Set Considerations

For MongoDB replica sets, exposing only one member might not be sufficient.

MongoDB drivers can discover replica-set members after connecting to an initial member.

Therefore, the externally advertised member addresses must also be reachable.

Example:

```text
MongoDB Replica Set

Member 0 -> External Port 30125
Member 1 -> External Port 30126
Member 2 -> External Port 30127
```

The driver must be able to connect to the advertised member addresses.

This requires careful consideration of:

- Replica-set advertised hostnames.
- External port mappings.
- TLS certificates and hostname validation.
- Replica-set discovery.
- Network connectivity to every required member.

For sharded MongoDB deployments, clients generally connect through `mongos`, so external routes are created for the mongos endpoints rather than individual shard members.

## 9. Security Considerations

External MongoDB connectivity must include multiple security controls.

| Area | Responsibility |
|---|---|
| Encryption | MongoDB TLS |
| Authentication | MongoDB users and authentication mechanisms |
| Authorization | MongoDB roles and privileges |
| Network restrictions | Cilium NetworkPolicy / firewall / ACL |
| Port allocation | Unique port ownership and collision prevention |
| Secrets | Vault / secret management |
| Connection management | Envoy and MongoDB connection limits |

Envoy TCP passthrough can preserve end-to-end MongoDB TLS, allowing MongoDB to handle TLS termination and certificate validation.

### Key Takeaways

1. MongoDB runs inside our Kubernetes infrastructure.
2. Customers connect remotely using standard MongoDB clients such as `mongosh`.
3. MongoDB uses the MongoDB Wire Protocol over TCP, not HTTP.
4. A generic TCP proxy cannot route using HTTP hostnames or URL paths.
5. We assign unique external ports to distinguish MongoDB endpoints.
6. Envoy Gateway provides the shared external TCP entry point.
7. TCPRoute maps external listener traffic to the correct MongoDB Service.
8. `liberty-gateway-operator` automates port allocation, ListenerSet creation and TCPRoute management.

**Core problem being solved:** How to expose hundreds of independently managed MongoDB instances running inside Kubernetes through a small number of shared external gateways while maintaining deterministic routing and tenant isolation.
