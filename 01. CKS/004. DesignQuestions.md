# Kubernetes Container Image Security

## 1. Core Concept

**Objective:** Prevent vulnerable or untrusted container images from reaching production and continuously monitor running workloads for newly discovered vulnerabilities.

### Problem Statement

Imagine an organization running:

- 50 Kubernetes clusters.
- 200 workloads per cluster.
- Multiple development teams and CI/CD pipelines.

We need a centralized security strategy to ensure:

1. Vulnerable images are detected before deployment.
2. Only trusted and approved images are deployed.
3. Running workloads are continuously monitored.
4. Newly discovered vulnerabilities are identified and remediated.

## 2. Architecture – Four Main Components

| Tool | Responsibility |
|---|---|
| **Trivy** | Scans container images for vulnerabilities. |
| **Kyverno** | Enforces Kubernetes security policies at admission time. |
| **Cosign** | Signs container images and security attestations. |
| **Trivy Operator** | Continuously monitors deployed workloads for vulnerabilities. |

**Note:** OPA/Gatekeeper is not required in this design. Kyverno handles our Kubernetes admission policy requirements.

## 3. How Does It Work?

<details>
<summary><strong>Step 1 – Build and Push Image</strong></summary>

Developers build container images and push them to a trusted container registry.

Example:

```bash
docker build -t myapp:v1 .
docker push registry.example.com/myapp:v1
```

</details>

<details>
<summary><strong>Step 2 – Scan Image Using Trivy</strong></summary>

Trivy scans the container image for:

- OS package vulnerabilities.
- Application dependency vulnerabilities.
- Known CVEs.
- Misconfigurations (when configured).

Example:

```bash
trivy image registry.example.com/myapp:v1
```

The scan identifies vulnerabilities and their severity levels.

</details>

<details>
<summary><strong>Step 3 – Approve or Reject Image</strong></summary>

CI/CD evaluates Trivy scan results against company security policies.

Example policy:

| Severity | Decision |
|---|---|
| Critical | Reject |
| High | Reject or require an approved exception |
| Medium | Allow or require remediation |
| Low | Allow and track |

If the image violates the security policy, the pipeline fails.

**Important:** Trivy detects vulnerabilities. CI/CD implements the approval or rejection decision.

</details>

<details>
<summary><strong>Step 4 – Sign Image Using Cosign</strong></summary>

After successful scanning, Cosign signs the approved image.

Example:

```bash
cosign sign \
  registry.example.com/myapp@sha256:IMAGE_DIGEST
```

We can also create and sign a vulnerability attestation:

```bash
cosign attest \
  --predicate vulnerability-report.json \
  --type vuln \
  registry.example.com/myapp@sha256:IMAGE_DIGEST
```

Why?

- Establish image authenticity.
- Verify the image came from a trusted build pipeline.
- Associate security evidence with the exact image digest.
- Prevent an unapproved image from being substituted after scanning.

</details>

<details>
<summary><strong>Step 5 – Enforce Policies Using Kyverno</strong></summary>

When a developer deploys an application, the Kubernetes API Server invokes admission controllers.

Kyverno evaluates the deployment against configured policies.

Examples:

1. Only allow images from trusted registries.
2. Reject images that are not signed by an approved identity.
3. Verify vulnerability attestations and their required conditions.
4. Require immutable image references using digests.

If verification fails, Kyverno rejects the deployment.

**Important:** Signature verification alone does not guarantee that an image has no critical vulnerabilities. Kyverno must also validate the relevant signed vulnerability attestation.

</details>

<details>
<summary><strong>Step 6 – Continuous Monitoring Using Trivy Operator</strong></summary>

Deploy Trivy Operator in every Kubernetes cluster.

It monitors deployed workloads and generates vulnerability reports.

It helps identify:

- Newly discovered CVEs.
- Vulnerable container images.
- Changes in vulnerability status.
- Workloads requiring remediation.

Findings can be exported or integrated with a centralized security platform.

**Important:** Trivy Operator detects vulnerabilities; it does not automatically patch application images.

</details>

## 5. Important Interview Questions

<details>
<summary><strong>Q1. Why do we need Trivy?</strong></summary>

Trivy scans container images and identifies known vulnerabilities in OS packages and application dependencies.

It helps detect vulnerable images before they reach production.

</details>

<details>
<summary><strong>Q2. Why do we need Kyverno?</strong></summary>

Kyverno enforces security policies at Kubernetes admission time.

It ensures that only images satisfying our deployment security requirements are allowed to run.

</details>

<details>
<summary><strong>Q3. Why do we need Cosign?</strong></summary>

Cosign signs container images and attestations.

It establishes image authenticity and allows Kubernetes admission policies to verify trusted signatures and security evidence.

</details>

<details>
<summary><strong>Q4. Why use immutable image digests?</strong></summary>

Image tags are mutable. The same tag can point to different images over time.

An image digest uniquely identifies the image content.

Using the same digest for scanning, signing and deployment ensures that the deployed image is the one that was approved.

</details>

<details>
<summary><strong>Q5. Why do we need Trivy Operator if CI/CD already scans images?</strong></summary>

CI/CD scans images before deployment.

However, new CVEs can be disclosed after an image is deployed.

Trivy Operator helps identify these newly discovered vulnerabilities in running workloads.

</details>

<details>
<summary><strong>Q6. Why not use OPA/Gatekeeper?</strong></summary>

OPA/Gatekeeper is another Kubernetes policy enforcement solution.

For this architecture, Kyverno is sufficient because it provides Kubernetes-native policy enforcement and image verification capabilities.

Using both would introduce unnecessary policy-engine complexity.

</details>

<details>
<summary><strong>Q7. What happens if Kyverno becomes unavailable?</strong></summary>

For mandatory production security controls:

- Run Kyverno with high availability.
- Configure appropriate admission webhook failure policies.
- Use `failurePolicy: Fail` for mandatory security checks.
- Monitor webhook availability and admission latency.

Fail-closed behavior prevents deployments when verification cannot be performed, but must be balanced against cluster availability requirements.

</details>

<details>
<summary><strong>Q8. What happens when a new CVE is discovered?</strong></summary>

Trivy Operator identifies the vulnerability during subsequent scanning.

The security platform identifies affected image digests and workloads.

Application teams are notified and build patched images.

The patched images go through the same scan, signing and admission verification process.

</details>

## 6. Important Scenario – New Critical CVE in Production

**Interview Question:**

Yesterday, an image was scanned and had zero critical vulnerabilities.

Today, a new critical CVE is discovered.

The image is already running in 10 production Kubernetes clusters.

What happens?

<details>
<summary><strong>Expand: End-to-end remediation workflow</strong></summary>

**Step 1 – Detect**

Trivy Operator rescans deployed images and identifies the newly discovered CVE.

**Step 2 – Identify affected images**

The central security platform identifies the affected image digest.

**Step 3 – Map affected workloads**

Identify all Deployments, StatefulSets and Pods using that image digest across the 10 clusters.

**Step 4 – Notify application owners**

Generate security alerts and assign remediation ownership.

**Step 5 – Build patched image**

Application teams update the vulnerable package or dependency and build a new image.

**Step 6 – Scan and approve**

Trivy scans the new image. CI/CD evaluates it against security thresholds.

**Step 7 – Sign**

Cosign signs the approved image and its vulnerability attestation.

**Step 8 – Deploy**

Kyverno verifies the image signature and required security attestation during admission.

**Step 9 – Confirm remediation**

The central security platform verifies that affected workloads are running the patched image digest.

**Important distinction:**

Kyverno prevents new non-compliant deployments. It does not automatically terminate or repair already-running vulnerable workloads.

Existing workloads require a remediation process.

</details>

## 7. Interview-Ready 60-Second Answer

<details>
<summary><strong>Expand: 60-second explanation</strong></summary>

I would implement a three-layer container image security strategy.

First, I would integrate Trivy into CI/CD to scan container images for OS and application dependency vulnerabilities. Images violating our security thresholds would be rejected.

Second, I would use Cosign to sign approved images and their security attestations. Kyverno would verify these signatures and enforce admission policies, ensuring only trusted and compliant images are deployed.

Third, I would deploy Trivy Operator in every Kubernetes cluster for continuous vulnerability monitoring because new CVEs can be disclosed even after deployment.

Finally, I would centralize vulnerability findings, map affected image digests to workloads across clusters, notify application owners and coordinate remediation.

This provides security across the image lifecycle: **Build → Scan → Sign → Verify → Monitor → Remediate.**

</details>
