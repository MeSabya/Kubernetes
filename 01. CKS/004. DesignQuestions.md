# Design a Centralized Policy Management System for 50 Kubernetes Clusters

## 1. Problem Statement

We manage 50 Kubernetes clusters used by multiple application teams.

We need a centralized system to:

- Enforce consistent security and compliance policies.
- Prevent insecure workloads from being deployed.
- Distribute policy changes across all clusters.
- Support environment-specific policies and exceptions.
- Monitor policy compliance centrally.
- Avoid manually managing policies in individual clusters.

**Goal:** Centralized policy governance with decentralized enforcement.

---

## 2. Proposed Architecture

We use:

| Component | Responsibility |
|---|---|
| Git | Central source of truth for policies |
| Flux CD | Distributes and reconciles policies across clusters |
| Kyverno | Validates and enforces Kubernetes policies |
| Pod Security Admission (PSA) | Enforces Kubernetes Pod Security Standards |
| VictoriaMetrics / Grafana | Centralized monitoring and reporting |

### Architecture

```text
             Central Git Repository
             (Policy as Code)
                      |
              Flux CD Source
                      |
          +-----------+-----------+
          |           |           |
          v           v           v
       Cluster 1   Cluster 2   Cluster 50
          |           |           |
        Flux CD     Flux CD     Flux CD
          |           |           |
       Kustomize   Kustomize   Kustomize
          |           |           |
       Kyverno     Kyverno     Kyverno
          |           |           |
       API Server  API Server  API Server
          |           |           |
       Policies    Policies    Policies
       Enforced    Enforced    Enforced

                 Central Monitoring
               VictoriaMetrics/Grafana
```

Each cluster runs its own Flux and Kyverno installation.

## 3. How Flux CD Works

Flux CD is a GitOps tool that continuously reconciles Kubernetes resources with the desired state stored in Git.

### Main components

| Component | Responsibility |
|---|---|
| Source Controller | Fetches Git repository changes |
| Kustomize Controller | Builds and applies Kubernetes manifests |
| Helm Controller | Manages Helm releases |
| Notification Controller | Sends alerts and receives events |

### Reconciliation flow

1. Platform team commits a policy change to Git.
2. Source Controller periodically checks the Git repository.
3. It downloads the latest revision and creates an artifact.
4. Kustomize Controller detects the updated artifact.
5. It builds the manifests from the configured repository path.
6. Flux applies the resources to the local Kubernetes API server.
7. Kyverno receives the policy resources and starts enforcing them.

Flux also periodically checks for configuration drift and reconciles the cluster.

**Important:** Flux distributes policies; Kyverno enforces them.

### Example: GitRepository

Each cluster has a GitRepository resource pointing to the central policy repository.

```yaml
apiVersion: source.toolkit.fluxcd.io/v1
kind: GitRepository
metadata:
  name: platform-policies
  namespace: flux-system
spec:
  interval: 1m
  url: https://github.com/company/platform-kubernetes-policies
  ref:
    branch: main
```

### Example: Flux Kustomization

This tells Flux which directory to reconcile.

```yaml
apiVersion: kustomize.toolkit.fluxcd.io/v1
kind: Kustomization
metadata:
  name: cluster-policies
  namespace: flux-system
spec:
  interval: 5m
  sourceRef:
    kind: GitRepository
    name: platform-policies
  path: "./policies/security"
  prune: true
  wait: true
```

**Key fields:**

- `sourceRef`: Git repository to consume.
- `path`: Directory containing policy manifests.
- `interval`: Reconciliation frequency.
- `prune`: Remove resources previously managed by Flux when deleted from the source.
- `wait`: Wait for applied resources to become ready.

### How policies reach all 50 clusters

We use the **per-cluster Flux model**.

- Every cluster has its own Flux controllers.
- All clusters point to the same central Git repository.
- When a policy changes, each cluster independently fetches the latest revision.
- Each cluster applies the policy locally.

No central server needs to SSH into 50 clusters or execute `kubectl apply` manually.

This provides independent enforcement and avoids making one management cluster a runtime dependency.

## 4. Example Policy: Disallow Privileged Containers

Kyverno ClusterPolicy:

```yaml
apiVersion: kyverno.io/v1
kind: ClusterPolicy
metadata:
  name: disallow-privileged
spec:
  validationFailureAction: Enforce
  background: true
  rules:
    - name: block-privileged-containers
      match:
        any:
          - resources:
              kinds:
                - Pod
      validate:
        message: "Privileged containers are not allowed."
        pattern:
          spec:
            containers:
              - securityContext:
                  privileged: false
```

When an application team deploys a privileged Pod:

1. Request reaches the Kubernetes API server.
2. Kyverno admission webhook evaluates the Pod.
3. The policy detects `privileged: true`.
4. Admission is rejected.

Note: Production policies should also cover init and ephemeral containers where relevant.

## 5. Policy Categories

| Category | Example policies |
|---|---|
| Container Security | Non-root, read-only filesystem, drop capabilities |
| Image Security | Approved registries, image signature verification |
| Resource Governance | CPU/memory requests and limits |
| Network Security | Restrict host networking, require NetworkPolicies |
| Secrets Security | Restrict secret access and enforce approved secret delivery |
| Compliance | Pod Security Standards, CIS requirements |

Use PSA for standard Pod Security requirements and Kyverno for additional custom organizational policies.

## 6. Progressive Policy Rollout

Do not enforce a new policy across all 50 clusters immediately.

Use progressive rollout:

| Stage | Clusters | Mode |
|---|---:|---|
| Development | 5 | Audit |
| Staging | 10 | Audit / Enforce |
| Production Canary | 5 | Enforce |
| Remaining Production | 30 | Enforce |

Flow:

```text
Policy Change
     |
     v
Development (Audit)
     |
     v
Staging (Validate)
     |
     v
Production Canary
     |
     v
All Production Clusters
```

Use separate Flux Kustomizations and environment-specific overlays to control rollout.

---

## 7. Exception Management

Some applications may need temporary exceptions.

Implement an approval-based exception process:

- Application team submits an exception request.
- Platform/security team reviews it.
- Exception includes justification and expiry.
- Exception is stored and reviewed through Git.
- Expired exceptions are removed.

Application teams must not be allowed to approve their own security exceptions.

---

## 8. Centralized Monitoring

We need to monitor two different dimensions:

| Monitoring | What it tells us |
|---|---|
| Flux reconciliation status | Did the cluster receive and apply the policy? |
| Kyverno PolicyReports | Are workloads compliant with the policy? |

Collect metrics and reports centrally using VictoriaMetrics and Grafana.

Example checks:

```bash
flux get sources git -A

flux get kustomizations -A
```

Monitor:

- Clusters that have not reconciled.
- Clusters running outdated policy revisions.
- Policy violations.
- Failed admission requests.
- Expired exceptions.

A successful Flux reconciliation does not necessarily mean every existing workload is compliant.

---

## 9. Failure Handling

**What happens if Git becomes unavailable?**

- Existing Flux controllers continue running.
- Existing Kyverno policies remain installed.
- Kubernetes admission continues enforcing installed policies.
- New policy changes cannot be distributed until Git connectivity is restored.
- Flux resumes reconciliation when connectivity returns.

This is an important benefit of local policy enforcement.

---

## 10. Security and Governance

- Restrict who can modify the central policy repository.
- Require PR reviews and automated policy tests.
- Protect production branches.
- Restrict application-team permissions over ClusterPolicy resources.
- Restrict creation and modification of Flux sources and Kustomizations.
- Use narrow service-account permissions for Flux.
- Keep Kyverno highly available.
- Carefully configure webhook failure behavior, especially for critical policies.

# Prevent Containers from Running as Root

## 1. Problem Statement

We have **100 application teams sharing Kubernetes infrastructure**.

Each team deploys multiple applications across shared Kubernetes clusters. We need to enforce a consistent security standard:

> **No application container should run as the root user (UID 0).**

### Challenges

- Developers may accidentally build images that run as root.
- Kubernetes settings can override the image's default user.
- Different teams may configure Pod security differently.
- A policy applied manually by teams can be removed or bypassed.
- We need centralized enforcement without relying on developer discipline.

### Goal

Design a defense-in-depth solution that:

1. Builds non-root container images.
2. Enforces non-root execution at Kubernetes admission.
3. Prevents teams from bypassing security policies.
4. Provides visibility into policy violations.
5. Scales consistently across all 100 teams.

---

## 2. Proposed Architecture

Use four layers of security enforcement:

| Layer | Component | Responsibility |
|---|---|---|
| Image | Dockerfile `USER` | Set a non-root default user |
| Runtime configuration | Kubernetes `securityContext` | Specify and validate the container UID |
| Admission control | Pod Security Admission (PSA) | Enforce Kubernetes Restricted security standards |
| Custom policy enforcement | Kyverno | Enforce organization-specific security rules |

### Architecture Flow

```text
                 100 Application Teams
                          |
                          v
                   Developer / CI
                          |
                          v
                 Build Container Image
                          |
                          v
                 Dockerfile: USER 10001
                          |
                          v
                  Container Registry
                          |
                          v
                 Kubernetes Deployment
                          |
                          v
                   Kubernetes API
                          |
                          v
                  Admission Control
                          |
              +-----------+-----------+
              |                       |
              v                       v
        PSA Restricted          Kyverno Policies
              |                       |
              |                 Require:
              |                 - runAsNonRoot: true
              |                 - Approved UID policy
              |                 - Additional security rules
              |                       |
              +-----------+-----------+
                          |
                   Admission Decision
                          |
                 +--------+--------+
                 |                 |
              Allowed            Rejected
                 |                 |
                 v                 v
             Pod Created       Policy Violation
                 |
                 v
              Kubelet
                 |
                 v
          Container Runtime
                 |
                 v
        Process runs as UID 10001
```

**Important:** PSA and Kyverno validate the Pod during admission. The kubelet and container runtime enforce the configured user identity when starting the container.

# Kubernetes Container Image Security

## 1. Core Concept

**Objective:** Prevent vulnerable or untrusted container images from reaching production and continuously monitor running workloads for newly discovered vulnerabilities.

### Problem Statement

Imagine an organization running:

- 50 Kubernetes clusters.
- 200 workloads per cluster.
- Multiple development teams and CI/CD pipelines.

We need a centralized security strategy to ensure:

1. Vulnerable images are detected before deployment.
2. Only trusted and approved images are deployed.
3. Running workloads are continuously monitored.
4. Newly discovered vulnerabilities are identified and remediated.

## 2. Architecture – Four Main Components

| Tool | Responsibility |
|---|---|
| **Trivy** | Scans container images for vulnerabilities. |
| **Kyverno** | Enforces Kubernetes security policies at admission time. |
| **Cosign** | Signs container images and security attestations. |
| **Trivy Operator** | Continuously monitors deployed workloads for vulnerabilities. |

**Note:** OPA/Gatekeeper is not required in this design. Kyverno handles our Kubernetes admission policy requirements.

## 3. How Does It Work?

<details>
<summary><strong>Step 1 – Build and Push Image</strong></summary>

Developers build container images and push them to a trusted container registry.

Example:

```bash
docker build -t myapp:v1 .
docker push registry.example.com/myapp:v1
```

</details>

<details>
<summary><strong>Step 2 – Scan Image Using Trivy</strong></summary>

Trivy scans the container image for:

- OS package vulnerabilities.
- Application dependency vulnerabilities.
- Known CVEs.
- Misconfigurations (when configured).

Example:

```bash
trivy image registry.example.com/myapp:v1
```

The scan identifies vulnerabilities and their severity levels.

</details>

<details>
<summary><strong>Step 3 – Approve or Reject Image</strong></summary>

CI/CD evaluates Trivy scan results against company security policies.

Example policy:

| Severity | Decision |
|---|---|
| Critical | Reject |
| High | Reject or require an approved exception |
| Medium | Allow or require remediation |
| Low | Allow and track |

If the image violates the security policy, the pipeline fails.

**Important:** Trivy detects vulnerabilities. CI/CD implements the approval or rejection decision.

</details>

<details>
<summary><strong>Step 4 – Sign Image Using Cosign</strong></summary>

After successful scanning, Cosign signs the approved image.

Example:

```bash
cosign sign \
  registry.example.com/myapp@sha256:IMAGE_DIGEST
```

We can also create and sign a vulnerability attestation:

```bash
cosign attest \
  --predicate vulnerability-report.json \
  --type vuln \
  registry.example.com/myapp@sha256:IMAGE_DIGEST
```

Why?

- Establish image authenticity.
- Verify the image came from a trusted build pipeline.
- Associate security evidence with the exact image digest.
- Prevent an unapproved image from being substituted after scanning.

</details>

<details>
<summary><strong>Step 5 – Enforce Policies Using Kyverno</strong></summary>

When a developer deploys an application, the Kubernetes API Server invokes admission controllers.

Kyverno evaluates the deployment against configured policies.

Examples:

1. Only allow images from trusted registries.
2. Reject images that are not signed by an approved identity.
3. Verify vulnerability attestations and their required conditions.
4. Require immutable image references using digests.

If verification fails, Kyverno rejects the deployment.

**Important:** Signature verification alone does not guarantee that an image has no critical vulnerabilities. Kyverno must also validate the relevant signed vulnerability attestation.

</details>

<details>
<summary><strong>Step 6 – Continuous Monitoring Using Trivy Operator</strong></summary>

Deploy Trivy Operator in every Kubernetes cluster.

It monitors deployed workloads and generates vulnerability reports.

It helps identify:

- Newly discovered CVEs.
- Vulnerable container images.
- Changes in vulnerability status.
- Workloads requiring remediation.

Findings can be exported or integrated with a centralized security platform.

**Important:** Trivy Operator detects vulnerabilities; it does not automatically patch application images.

</details>

## 5. Important Interview Questions

<details>
<summary><strong>Q1. Why do we need Trivy?</strong></summary>

Trivy scans container images and identifies known vulnerabilities in OS packages and application dependencies.

It helps detect vulnerable images before they reach production.

</details>

<details>
<summary><strong>Q2. Why do we need Kyverno?</strong></summary>

Kyverno enforces security policies at Kubernetes admission time.

It ensures that only images satisfying our deployment security requirements are allowed to run.

</details>

<details>
<summary><strong>Q3. Why do we need Cosign?</strong></summary>

Cosign signs container images and attestations.

It establishes image authenticity and allows Kubernetes admission policies to verify trusted signatures and security evidence.

</details>

<details>
<summary><strong>Q4. Why use immutable image digests?</strong></summary>

Image tags are mutable. The same tag can point to different images over time.

An image digest uniquely identifies the image content.

Using the same digest for scanning, signing and deployment ensures that the deployed image is the one that was approved.

</details>

<details>
<summary><strong>Q5. Why do we need Trivy Operator if CI/CD already scans images?</strong></summary>

CI/CD scans images before deployment.

However, new CVEs can be disclosed after an image is deployed.

Trivy Operator helps identify these newly discovered vulnerabilities in running workloads.

</details>

<details>
<summary><strong>Q6. Why not use OPA/Gatekeeper?</strong></summary>

OPA/Gatekeeper is another Kubernetes policy enforcement solution.

For this architecture, Kyverno is sufficient because it provides Kubernetes-native policy enforcement and image verification capabilities.

Using both would introduce unnecessary policy-engine complexity.

</details>

<details>
<summary><strong>Q7. What happens if Kyverno becomes unavailable?</strong></summary>

For mandatory production security controls:

- Run Kyverno with high availability.
- Configure appropriate admission webhook failure policies.
- Use `failurePolicy: Fail` for mandatory security checks.
- Monitor webhook availability and admission latency.

Fail-closed behavior prevents deployments when verification cannot be performed, but must be balanced against cluster availability requirements.

</details>

<details>
<summary><strong>Q8. What happens when a new CVE is discovered?</strong></summary>

Trivy Operator identifies the vulnerability during subsequent scanning.

The security platform identifies affected image digests and workloads.

Application teams are notified and build patched images.

The patched images go through the same scan, signing and admission verification process.

</details>

## 6. Important Scenario – New Critical CVE in Production

**Interview Question:**

Yesterday, an image was scanned and had zero critical vulnerabilities.

Today, a new critical CVE is discovered.

The image is already running in 10 production Kubernetes clusters.

What happens?

<details>
<summary><strong>Expand: End-to-end remediation workflow</strong></summary>

**Step 1 – Detect**

Trivy Operator rescans deployed images and identifies the newly discovered CVE.

**Step 2 – Identify affected images**

The central security platform identifies the affected image digest.

**Step 3 – Map affected workloads**

Identify all Deployments, StatefulSets and Pods using that image digest across the 10 clusters.

**Step 4 – Notify application owners**

Generate security alerts and assign remediation ownership.

**Step 5 – Build patched image**

Application teams update the vulnerable package or dependency and build a new image.

**Step 6 – Scan and approve**

Trivy scans the new image. CI/CD evaluates it against security thresholds.

**Step 7 – Sign**

Cosign signs the approved image and its vulnerability attestation.

**Step 8 – Deploy**

Kyverno verifies the image signature and required security attestation during admission.

**Step 9 – Confirm remediation**

The central security platform verifies that affected workloads are running the patched image digest.

**Important distinction:**

Kyverno prevents new non-compliant deployments. It does not automatically terminate or repair already-running vulnerable workloads.

Existing workloads require a remediation process.

</details>

## 7. Interview-Ready 60-Second Answer

<details>
<summary><strong>Expand: 60-second explanation</strong></summary>

I would implement a three-layer container image security strategy.

First, I would integrate Trivy into CI/CD to scan container images for OS and application dependency vulnerabilities. Images violating our security thresholds would be rejected.

Second, I would use Cosign to sign approved images and their security attestations. Kyverno would verify these signatures and enforce admission policies, ensuring only trusted and compliant images are deployed.

Third, I would deploy Trivy Operator in every Kubernetes cluster for continuous vulnerability monitoring because new CVEs can be disclosed even after deployment.

Finally, I would centralize vulnerability findings, map affected image digests to workloads across clusters, notify application owners and coordinate remediation.

This provides security across the image lifecycle: **Build → Scan → Sign → Verify → Monitor → Remediate.**

</details>
